# Design: Offline Sync and Resilience

## Decisions

- Cache only published, entitled lesson payloads with content revision and expiry metadata. `Lesson.ContentRevision` (int, concurrency token) is bumped on every lesson edit and on each course (re)publish, so a cached client always knows which revision it cached against.
- Queue progress events with a client-generated idempotency key (`OperationId`). The optional `ContentRevision` field is the revision the client cached against; if it is older than the lesson's current revision, the event is retained as a `conflict` rather than silently applying progress against stale content.
- Server processing is idempotent per `OperationId`. Lesson completion is monotonic (recorded once), while editable learner notes use server `UpdatedAt.Ticks` as a base version and report explicit conflicts with canonical state. `MobileSyncService.RecordAsync` is the single write path for both the per-item and batch endpoints.
- A `POST /api/mobile/v1/sync/batch` endpoint accepts a heterogeneous batch of `progress.complete` and `note.upsert` items and returns one `SyncResult` per input item in input order. Each item is processed independently in its own `try`/`catch`; one bad item never aborts the rest of the batch and never produces an exception in the response (an unknown type is recorded as `rejected` with the parse error captured in `CanonicalState`).
- Sync responses report outcomes `applied`, `duplicate`, `rejected`, and `conflict` per item. The batch endpoint is the primary path; the per-item endpoints stay for clients that haven't migrated yet.

## Security

Every sync request rechecks identity, enrollment/access period, tenant scope, and content entitlement. Cached private data is encrypted or protected by the platform storage mechanism and is removed on sign-out where supported. The batch endpoint runs each item through the same authorization path as the per-item endpoints, so revoked access or expired enrollment is surfaced as `rejected` for the offending item without affecting peers.

## Verification

- `tests/.../MobileApiTests.cs` covers retries, duplicates, stale content revision → `conflict`, current revision → `applied`, missing revision (legacy clients) → `applied`, and batch partial failure (one `applied`, one `rejected` for wrong-course, one `conflict` for stale revision) with valid items retained.
- Schema migration `20260922083528_AddLessonContentRevision` is generated by EF; the new column has a server default of `1` so existing rows backfill cleanly.

## Out of scope for this repository

The client-side requirements in the original proposal (bounded lesson cache, local progress queue, retry policy, network transition handling, sync status UI) live in the mobile client codebase, not in this .NET server. They remain tracked against the mobile client repo and are not implemented here. Likewise, the visible `Offline / Pending sync / Synced / Sync failed` UI states are the mobile client's responsibility; the server already provides the per-item outcomes the client needs to render them.
